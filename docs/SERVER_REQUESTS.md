# 端末からサーバー担当へのお願い(2026-11-17)

書いた人: ハード担当 / 状態: **案(形は相談して決めたい)**

端末のファームを、T-Beam 1 枚で動く形に作り直すことになりました。
それに合わせて、**今のサーバー(`Re-Ray_Server` の 11/10 時点)に無くて、端末に要るもの**をまとめます。
端末側の設計の全体は、[re-ray-device](https://github.com/tkitora/re-ray-device) の `docs/DESIGN.md` にあります。

## 1. 何が変わったか(11/17 にリーダーが決めたこと)

| 項目 | 内容 |
|---|---|
| 端末 | T-Beam 1 枚。ボタン 3 つ(戻る・選択・決定)とピンマイクを付ける。表示は GUIDE01 |
| 平常時 | **トランシーバーのように使う。** 端末が話した声をサーバーに送り、サーバーが文字にして、宛先に配る |
| 緊急時 | 決まった信号と SOS を送る。音声は送らない。端末のボタン 3 つの同時押しで切り替える |
| チャンネル | その端末が見られるメッセージのグループ。**本部との 1 対 1** と、**複数の端末が入るグループ**がある。**端末ごとに、管理画面から設定する** |

## 2. 今のサーバーに合わせて、端末がそのまま使うもの

サーバーの `src/protocol/validate.ts` を読んで、次の形に合わせて作ります。変更のお願いはありません。

- 接続: クライアント ID = `dev-001` の形、clean session = false、keepalive 30 秒、遺言つき
- 状態(30 秒ごと)、定型信号(`code`、`pos`、`n`、`dir`、`via`)、返事(`ack_mid`、`ack_kind` 3 / 4 / 5)
- 番号(seq)は起動のたびに乱数から。時刻(ts)が分からないときは 0
- サーバーからの「本部に届いた」(`down/{id}/ack`)を待ち、来なければ同じ番号で送り直す
- 「了解」「できない」(`ack_kind` 4・5)は、**端末から送ります**(返事が要る指示が届いたら、ボタンで選ぶ)。11/09 の文書の質問への答えです

## 3. お願いしたいもの

| # | 要るもの | 端末から見た形(案) | サーバーに無い間、端末はどう動くか |
|---|---|---|---|
| 1 | **チャンネル**(表、どの端末が入るか、管理画面での設定) | — | 「本部」と「全体」の 2 つとして動く |
| 2 | チャンネルの一覧を端末に配る | トピック `reray/v1/down/{id}/config`。つないだ直後にも届くように、保持つき(retain)で流す | 同上 |
| 3 | 文に、チャンネルと話した人を付ける。グループの文は、**参加している端末 1 台ずつ**に配る | text に `ch`、`from`、`from_name` を足す | `ch` が無い文は、個別あて = 本部、全員あて = 全体 に入れる |
| 4 | **音声の受け口と、文字起こし** | `POST /api/voice`(下の §4) | 音声は送れない(「準備中」と出す) |
| 5 | モード(平常時 / 緊急時) | 状態(status)に `mode` を足す。本部から全端末を切り替える `reray/v1/down/all/mode` | 端末のボタンでの切り替えだけ |
| 6 | 外からつなぐための、認証と暗号化 | MQTT と HTTP に、端末ごとのユーザー名・パスワード(またはトークン)と TLS | 同じ LAN の中だけで試す |
| 7 | ポジションの一覧を端末に配る | 2 の `config` に入れる | `pos` は 0 で送る |
| 8 | LoRa のフレームの分解と、署名の検証 | `GATEWAY_RAW_FORMAT` のとおり | LoRa で届いた信号は、記録だけ残る |

急ぐ順は、**4(音声)→ 1〜3(チャンネル)→ 6(外からつなぐ)** です。5・7・8 はそのあとで大丈夫です。
1〜3 が無くても、端末は今のサーバーのままで結合テストができるように作ります。

## 4. 形の案

### 4.1 チャンネルの一覧(サーバー → 端末)

```json
{"v":1,"type":"config","rev":12,
 "channels":[{"ch":1,"kind":"direct","name":"本部"},
             {"ch":5,"kind":"group","name":"北班"}]}
```

- `rev` は、設定を変えるたびに増える番号。端末は、前より新しいときだけ覚え直す
- `kind`: `direct` = 本部とこの端末の 1 対 1、`group` = グループ
- 端末の都合での上限(案): チャンネルは 8 個まで、名前は全角 8 文字まで、全体で 1,500 バイトまで

### 4.2 チャンネルの文(サーバー → 端末)

今の text に、3 つ足します。

```json
{"v":1,"type":"text","src":"pc","dst":"dev-001","seq":8,"mid":13,"ts":1791849700,
 "ch":5,"from":"dev-003","from_name":"山田","body":"北口の点検が終わりました"}
```

- `ch`: どのチャンネルの文か
- `from`、`from_name`: だれが言ったか。本部からなら `pc` と「本部」
- **話した本人にも配ってほしい**です。どう聞き取られたかを、本人がグラスで確かめられます
- 返事(`ack_mid`)は、今と同じように端末ごとに返します。「何台に届いたか」は、今の数え方のまま使えるはずです

### 4.3 音声(端末 → サーバー)

```
POST /api/voice
  Content-Type: audio/wav         (16kHz、16 ビット、モノラル、圧縮なし)
  X-Device: dev-001               (話した端末)
  X-Channel: 5                    (宛先のチャンネル)
  X-Seq: 123                      (端末の番号。同じ番号がもう一度来たら、送り直し)
  本体: WAV(最長 15 秒 = 約 480KB)

返事: 202  {"id": 45}             (受け取った。文字起こしは、このあとで行う)
```

- 文字起こしが終わったら、4.2 の形で、そのチャンネルに入っている端末に配ってください。
- MQTT ではなく HTTP にした理由: 今のブローカーとサーバーは、1 通を 4KB までにしているためです。
- 文字起こしをどこで動かすか(自宅サーバーの中か、外のサービスか)は、おまかせします。今ある「文字になったものを受け取る口」(`source = transcript`)の手前に、音を文字にする処理を足す形になると思います。
- 端末のマイクは、ピンマイクを AD 変換で読む作りで、音の質はまだ分かりません。**録音した WAV の見本ができたら渡します。** 文字起こしが通るかを、先に確かめたいです。
- 本文の上限(今は 40 文字)は、文字起こしの文だと足りなくなりそうです。グラスは、長い文をページに分けて出せるように作ります。上限をいくつにするか、相談させてください。

### 4.4 モード

```json
(端末 → サーバー)状態に足す:      "mode":"normal"  または  "mode":"emergency"
(サーバー → 全端末)一斉の切り替え:  {"v":1,"type":"mode","src":"pc","seq":9,"ts":1791849700,"mode":"emergency"}
```

## 5. こちらから渡せるもの

| もの | いつ |
|---|---|
| 端末が送る JSON の見本(状態・定型信号・返事) | 端末の MQTT ができたら。今のサーバーの検証を通ることを、こちらでも確かめます |
| 録音した WAV の見本 | マイクを付けたら |
| LoRa のフレームの見本(署名つき、鍵と、分解した正しい結果のセット) | 8 に着手するとき |

## 6. 聞きたいこと

1. 自宅サーバーに、端末は**外からつなぎますか**(会場の Wi-Fi やテザリングから、インターネットごしに)。それとも、同じ LAN の中だけですか。6 の要る・要らないが決まります。
2. チャンネルと音声は、いつごろ着手できそうですか。結合テストの範囲を、それに合わせて決めたいです。
3. 4 の形で、困るところはありますか。
