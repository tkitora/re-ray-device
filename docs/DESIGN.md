# Re-Ray 端末ファームウェア 設計(T-Beam 単体・第 3 版)

作成: 2026-11-17 / 状態: **実装中の設計(§13 の未決は仮の扱いで進める)** / 書いた人: ハード担当

T-Beam 1 枚で動く端末ファームを、新しいリポジトリで作り直すための設計。
前のリポジトリ(`tkitora/re-ray`)は消してあり、このリポジトリ(`tkitora/re-ray-device`)で作り直す。前の中身は、リーダーの手元にバックアップがある。

確認度の書き方: **実機確認** = 手元の T-Beam で動かして確かめた / **資料確認** = 公式資料やコードで確かめた / **要確認** = まだ確かめていない / **案** = こちらの提案で、相手(サーバー担当など)の合意が要る。

---

## 0. 決まっていること(2026-11-17、リーダーの指示)

| 項目 | 決定 |
|---|---|
| 構成 | T-Beam 1 枚。通信は LoRa(ほかの端末)、BLE(GUIDE01)、MQTT(自宅サーバー) |
| 操作 | ボタン 3 つ(戻る・選択・決定)。GUIDE01 のタッチでも同じ操作ができる |
| モード | **平常時**はトランシーバーのように使う(話した声をサーバーに送り、サーバーが文字にして宛先へ配る)。**緊急時**は災害用の使い方。3 つ同時押しで切り替える |
| チャンネル | その端末が見られるメッセージのグループ。本部との 1 対 1 のチャンネルと、複数の端末が入るグループのチャンネルがある。**端末ごとに、管理画面(web)から設定する** |
| 画面 | 最初の画面から「チャンネルを見る」か「メッセージを送る」へ進む |
| チャンネルを見る | チャンネルを選んで決定 → 選択・決定ボタンで上下にスクロールして読む |
| メッセージを送る | 送り先はサーバーで固定。タイプ → 詳細 → 決定で送信 |
| 外付け | ユニバーサル基板に、ボタン 3 つ、乾電池ケース、**ピンマイク**をつなぐ口を付ける |
| 緊急時の音声 | **送らない**(まずこの形で作る) |

この設計で新しく必要になったもの(指示から導いたこと):

- **マイク。** T-Beam にも GUIDE01 にもマイクが無い(GUIDE01 の SDK に音声の機能は無い。資料確認)。ピンマイクを用意して、ユニバーサル基板につなぐ(§1.3)。
- **サーバー側の追加。** チャンネル、音声の受け口と文字起こし、モードの記録は、今のサーバーに無い(11/10 時点のコードで確認)。必要なものを §9 にまとめた。

## 1. ハード

```
              BLE                          LoRa 920MHz
 [GUIDE01] <------> [ T-Beam V1.2 ] <------------------> ほかの T-Beam
  表示・タッチ          |     ^
                Wi-Fi  |     |  ユニバーサル基板
          MQTT + HTTP  v     |   ├ ボタン: 戻る・選択・決定
              [自宅サーバー]   |   ├ ピンマイクの口 + マイクアンプ
                             └── └ 乾電池ケース + 5V 電源
```

### 1.1 この T-Beam で確かめてあること(実機確認、2026-11-06)

電源 IC は AXP2101(I2C 0x34)、LoRa は SX127x、GPS は動く、基板のボタン GPIO38(押すと 0)、LED GPIO4(LOW で点灯)、
PSRAM 約 4MB、BLE で **GUIDE01 への接続・電池の取得・文字の表示・タッチの受信**(T-Beam 単体)。

### 1.2 ピンの割り当て(案)

使えるピンは多くない。LoRa・GPS・電源 IC・LED・基板のボタン・PSRAM が使っているピンを除くと、
出力もできるピンが 13・14・25・15・2・0、入力だけのピンが 36・39 になる(公式 `utilities.h` とピン表に「使用中」として出てこないことを資料確認。
**ヘッダのどの穴に出ているかは、基板の印字で要確認**)。

| 役目 | GPIO(案) | 配線 |
|---|---|---|
| ボタン: 戻る | 13 | ボタン — GND。内蔵プルアップ(押すと 0) |
| ボタン: 選択 | 14 | 同上 |
| ボタン: 決定 | 25 | 同上 |
| マイク(アンプの出力) | 36 | アナログ入力。入力専用のピンで、Wi-Fi と同時に使える側の AD 変換(ADC1) |
| 予備 | 39 | 入力専用。電池の電圧を測るときに使える |

- ピンマイクにしたので、マイクの信号は 1 本で済み、ボタンは抵抗なしでつなげる。
- GPIO15・2・0 は、起動や書き込みに関わるので使わない。
- ボタンが付くまでは、**シリアルのキー(b / s / k / e)で同じ操作**ができるようにする(はんだ付けの前に画面を試せる)。

### 1.3 マイク(ピンマイク)

ピンマイクをつなぐ(2026-11-17 に決定)。**買う前に確かめること**がある。

| 確かめること | 理由 |
|---|---|
| **有線で、3.5mm のプラグ**のものを選ぶ | USB 接続や Bluetooth 接続のピンマイクは、T-Beam にはつなげない(この設計の対象外) |
| プラグが 3 極か 4 極か | 4 極(スマホ用)は、線の並びが製品で違う。ジャックの配線が変わる |
| 「プラグインパワー」が要るか、何ボルトか | ピンマイクの多くは、つなぐ側から数ボルトの電源をもらって動く。基板側で用意する |

つなぎ方(案):

```
 ピンマイク --3.5mm ジャック--> 電源(抵抗で 3.3V から)+ マイクアンプ --> GPIO36
```

- ピンマイクの出力はとても小さいので、**マイクアンプ**(数十倍に大きくする部品)が要る。アンプの基板は、外からマイクをつなげるものを選ぶ(基板にマイクが付いているだけの製品は、そのままでは使えない)。型番は、ピンマイクが決まってから選ぶ。
- ESP32 の AD 変換は雑音が多めなので、**文字起こしの精度が足りるかは、録音して確かめる**(作る順番の 6)。足りなければ、音をデジタルに変える部品(I2S の AD 変換基板)に替える。そのときは信号が 3 本になり、ピンの割り当てを見直す。
- 実機では未確認。

### 1.4 電源(乾電池)

| 事実 | 出典 |
|---|---|
| USB 入力の電圧は 3.9〜6V | 公式 `t_beam_hw.md`(資料確認) |
| 電池ホルダーは 3.7V のリチウム電池用で、USB をつなぐと充電される | 同上 |
| 止まっている状態からは、PWR ボタンで起動する | 同上。11/06 に実機でも、PWR を押すまで動かなかった |

- **乾電池を電池ホルダー(18650 の端子)につながない。** USB をつないだときに乾電池を充電してしまい、液漏れ・発熱の危険がある。
- 乾電池は **5V に整えてから USB 側に入れる。**
  - 案 A: 単 3 × 3〜4 本 + 5V の DC-DC モジュール → T-Beam の 5V 入力。直結はしない(4 本だと新品で 6V を超え、減ると 3.9V を割る)
  - 案 B: 市販の乾電池式モバイルバッテリー(単 3 × 4 → USB 5V)を USB ケーブルでつなぐ。はんだ付けが要らない
- 要確認: ヘッダの 5V ピンが USB 入力と同じ線か(回路図)。Wi-Fi の送信と録音が重なったときに電圧が落ちないか(実測)。電池を入れ替えたあと PWR を押す必要があるか(実機)。
- 電池の残りは、電源 IC では測れない。状態(status)の `battery` は省く(共通仕様で省略できる)。

## 2. モード

| | 平常時 | 緊急時 |
|---|---|---|
| 使い方 | トランシーバー。声で話し、文字で読む | 災害用。決まった信号と SOS を送る |
| 送れるもの | **音声**、定型信号(了解・到着など) | **SOS**、定型信号(無事・応援・要救助・負傷・食料・移動など)。**音声は送らない** |
| 経路 | Wi-Fi(MQTT と HTTP)だけ | Wi-Fi。だめなら LoRa(端末どうしで中継) |
| LoRa | 受信だけ(緊急の信号を聞いたら知らせる) | 受信・中継・送信(送信は §8.3 のガードの内側) |
| GPS | 止める(電池の節約) | 動かす。取れた位置を状態に付ける |
| 画面の 1 行目 | チャンネル名など | 「緊急」と出す |
| LED | 点灯 = つながっている | 速い点滅 |

- **切り替え方:** 3 つのボタンを同時に 1.5 秒 → 「緊急モードに切り替えますか  決定 = はい  戻る = いいえ」→ 決定。戻すときも同じ。
- モードは本体に覚えさせる(電源を入れ直しても同じモードで始まる)。
- 切り替えたら、サーバーに知らせる(状態に `mode` を付ける。案)。
- **本部から全端末を一斉に切り替える**こともできるようにする(案。§9)。災害のとき、全員が自分で切り替えるとは限らないため。
- 緊急時に音声を送らない理由: 回線が細いときに大きなデータを流さないため。企画の「緊急時の連絡は短い定型信号で」に合わせた。Wi-Fi が生きていれば送れるようにもできる(§13)。
- 操作のしかた(ボタンの意味、画面の進み方)は、**平常時も緊急時も同じ**にする。変わるのは、送れるものの一覧と、経路。

## 3. 操作

| 操作 | ボタン | GUIDE01 のタッチ(案) |
|---|---|---|
| 戻る | 戻る | 後ろへスワイプ |
| 選択 | 選択 | 1 回タップ、前へスワイプ |
| 決定 | 決定 | 2 回タップ |
| 話す | **決定を押している間**(§5.3) | 2 回タップで始め、もう一度 2 回タップで終わる |
| モードの切り替え | 3 つ同時に 1.5 秒 | 割り当てない(誤操作を防ぐ) |

- ボタンから来てもタッチから来ても、同じ「操作」に直してから画面に渡す。
- ボタンは 30 ミリ秒のチャタリング除去。1 つのボタンの操作は**離したとき**に出す。3 つがそろって 1.5 秒たったら「切り替え」を 1 回だけ出し、そのあと離したときの操作は出さない。
- 決定を 0.5 秒以上押し続けたら「長押し」とみなす(話す画面だけで使う)。
- タッチは、同じ通知が 3 回続けて届く(実機確認。原因は未確認)。0.3 秒以内の同じ通知は 1 回にまとめる。前へスワイプと長押しは、割り当ての前に実機で受信を確かめる。

## 4. 画面

### 4.1 流れ

```
 ホーム
 ├ チャンネルを見る → チャンネル一覧 → メッセージを読む
 │                    選択 = 次        選択 = 下へ  決定 = 上へ  戻る = 一覧へ
 │                    決定 = 開く
 └ メッセージを送る → ① タイプ → ② 詳細 → ③ 確認 → 結果
                      選択 = 次の候補  決定 = 進む  戻る = 1 つ前
                      ③ で 決定 = 送信(音声は、押している間 話す)

 どの画面でも: 3 つ同時押し = モードの切り替え。新しいメッセージは上にかぶせて知らせる。
```

### 4.2 画面ごとのボタン

| 画面 | 戻る | 選択 | 決定 |
|---|---|---|---|
| ホーム | 何もしない | 次の項目へ | 進む |
| チャンネル一覧 | ホームへ | 次のチャンネルへ(最後の次は最初) | 開く(いちばん新しい所から) |
| メッセージを読む | 一覧へ | 下へ(新しい方へ) | 上へ(古い方へ) |
| 送る ① タイプ | ホームへ | 次の候補へ | 決めて進む |
| 送る ② 詳細 | ① へ | 次の候補へ | 決めて進む |
| 送る ③ 確認 | ② へ | 何もしない | 送信(音声は §5.3) |
| 結果 | ホームへ | 何もしない | ホームへ |
| 届いた知らせ | あとで | (返事が要る指示だけ)できない | 閉じる / 了解 |

### 4.3 表示の決まり

- 画面は 624 × 405、文字を置ける高さは 340(実機確認)。1 回の表示は文字の部品 4 つまで(4 つで 1 回の書き込みに収まることを実機確認)。
- 並び(案): 1 行目 = 状態(モード、チャンネル名、つながり)、2〜4 行目 = 中身。
- **1 行に入る文字数は、まだ決められない。** 分かっているのは「サイズ 32 で半角の数字が 15 桁くらいで切れる(折り返さない)」「日本語 8 文字の行は正常」まで(11/06、目視、参考値)。
  折り返しの部品は、文字サイズと幅を定数で持ち、測り直した値を入れるだけで直せるようにする。測定は実装の最初に行う。
- 長い文は折り返して、3 行ごとのページに分ける。文字起こしの文は長くなるので、**読む画面のスクロールはページ単位**にする。

### 4.4 届いたときの知らせ

| 届いたもの | 表示 | ボタン |
|---|---|---|
| チャンネルの新しい文(声を文字にしたもの、本部からの文字) | 上にかぶせて「北班 山田: …」と出す | どれでも = 閉じる。閉じなくてもチャンネルに入る |
| 返事が要る指示 | 「指示: 北口へ移動」 | 決定 = 了解、選択 = できない、戻る = あとで |
| 本部からのモードの切り替え | 「本部から: 緊急モードに切り替えます」 | 自動で切り替わる。どれでも = 閉じる |

届いた時点で、「受け取った」は自動で返す。読んでいる最中・話している最中は、知らせを 1 行にとどめる。

## 5. チャンネル

### 5.1 考え方

- チャンネルは、サーバーが持つ。**どの端末がどのチャンネルを見られるかは、管理画面で端末ごとに決める。**
- 端末は、自分が見られるチャンネルの一覧をサーバーから受け取って覚える(電源を入れ直しても、Wi-Fi が無くても残る)。
- 種類は 2 つ: **1 対 1**(本部とこの端末)、**グループ**(複数の端末と本部)。
- 端末の中だけのチャンネルが 1 つある: **送った記録**(自分が送った定型信号と、届いたかどうか)。

### 5.2 端末が受け取るもの(案。§9 でサーバー担当に依頼)

チャンネルの一覧(つないだときと、管理画面で変えたときに届く):

```json
{"v":1,"type":"config","rev":12,
 "channels":[{"ch":1,"kind":"direct","name":"本部"},
             {"ch":5,"kind":"group","name":"北班"}]}
```

チャンネルの文(今の text に、`ch` と、だれが言ったかを足す):

```json
{"v":1,"type":"text","src":"pc","dst":"dev-001","seq":8,"mid":13,"ts":1791849700,
 "ch":5,"from":"dev-003","from_name":"山田","body":"北口の点検が終わりました"}
```

- グループの文は、サーバーが**参加している端末 1 台ずつ**に配る(端末は、今と同じ「自分あて」を聞くだけでよい。「何台に届いたか」の数え方もそのまま使える)。
- 自分が話した文も、文字になって自分に返ってくる(どう聞き取られたかを本人が確かめられる)。
- 上限(案): チャンネルは 8 個まで、名前は全角 8 文字まで、各チャンネルは新しい順に 30 件まで覚える(メッセージは電源を切ると消える)。
- `ch` が付いていない文(今のサーバーのまま)は、個別あてなら 1 対 1 のチャンネル、全員あてなら「全体」に入れる。**サーバーの追加を待たずに、端末側を先に作って試せる。**

### 5.3 話す(平常時)

1. 「メッセージを送る」→ ① タイプで **音声** → ② 詳細で **宛先のチャンネル** → ③「決定を押している間、話してください」
2. 決定を押している間、録音する。画面に「録音中 3 秒」と出す。離すと送る。最長 15 秒(超えたら自動で止めて送る)。
3. 送っている間は「送信中」。サーバーが受け取ったら「送りました」。
4. 少しして、文字になった文がそのチャンネルに届く。

近道(案): **チャンネルを読んでいる画面で決定を長押し**すると、そのチャンネルに向けてすぐ話せる(短く押すと、今までどおり上へスクロール)。トランシーバーらしい速さにするため。

| 項目 | 値(案) |
|---|---|
| 音の形式 | 16kHz、16 ビット、モノラル、圧縮なし(WAV)。1 秒で約 32KB、15 秒で約 480KB |
| ためる場所 | PSRAM(約 4MB ある。実機確認) |
| 送り方 | Wi-Fi の HTTP で、録音が終わってからまとめて送る(§9 の受け口)。MQTT には載せない(サーバーの MQTT は 1 通 4KB まで) |
| Wi-Fi が無いとき | 「音声は Wi-Fi が必要です」と出して、送らない。LoRa では音声を運ばない |

## 6. メッセージを送る

送り先は、どれもサーバー。① のタイプは、モードで変わる。

**平常時**

| ① タイプ | ② 詳細 | 送られるもの |
|---|---|---|
| 音声 | 宛先のチャンネル | 録音(§5.3) |
| 了解 | なし | 定型信号 code 3 |
| 到着 | なし | code 4 |
| 移動します | 方角 | code 9 |

**緊急時**

| ① タイプ | ② 詳細 | 送られるもの |
|---|---|---|
| SOS | なし(③ の確認だけ) | code 1。届くまで送り直す |
| 無事 | なし | code 2 |
| 応援を頼む / 要救助者あり / 負傷者あり | 人数 | code 5 / 6 / 7 |
| 食料がほしい | 食数 | code 8 |
| 到着 / 移動します / 了解 | なし / 方角 / なし | code 4 / 9 / 3 |

- コードと名前は、サーバーの一覧(`db/init/02_seed.sql`。仮の 9 個)に合わせた。一覧が変わったら、端末の表(`codes.h`)を同じに直す。
- 人数・食数・方角の選択肢と送る値(`n`、`dir`)は、サーバーの `SIGNAL_FORMAT` と読み合わせてから決める(要確認)。
- ポジション(`pos`)は、最初は 0(なし)で送る。ポジションの一覧を端末に配る方法が決まったら、② に足す(§9)。
- 定型信号を送ったあと: 「送信中」→ サーバーの返事が来たら「本部に届いた」。来なければ 5・10・20 秒後に**同じ番号で**送り直す。それでもだめなら「届いていない」と出して取っておき(8 件まで)、つながったときに送る。

## 8. 通信

### 8.1 MQTT と HTTP(自宅サーバー)

今のサーバーの実装(`Re-Ray_Server` の `validate.ts`、11/10 時点)に合わせる。**太字は、今のサーバーに無い項目(案)。**

| 項目 | 値 |
|---|---|
| つなぎ方 | **MQTT を、暗号化つきの WebSocket(wss、443 番)に載せる**(下の「自宅サーバーへの道」)。同じ LAN の中で試すときは、暗号化なしの MQTT(1883 番)にも切り替えられる |
| 名前とパスワード | 名前 = 端末 ID(`dev-001`)。パスワードは端末ごと。ブローカーは、端末が自分の分のトピックだけを使えるように制限する |
| クライアント ID | 端末 ID(`dev-001` の形) |
| 接続 | MQTT 3.1.1、clean session = false、keepalive 30 秒、受信の入れ物 2048 バイト。送るのは QoS 1(esp-mqtt は対応している) |
| 遺言 | `reray/v1/up/{id}/status` に `{"v":1,"type":"status","src":"{id}","online":false}`、QoS 1 |
| 購読 | `reray/v1/down/{id}/#` と `reray/v1/down/all/#` |
| 状態(30 秒ごと) | `seq`、`ts`、`glass`、**`mode`**、緊急時に位置が取れていれば `lat`・`lon`。`battery` は省く |
| 定型信号 | `code`、`pos`、要るときだけ `n`・`dir`、`via` は `wifi` |
| 返事 | `ack_mid`、`ack_kind`(3 受け取った / 4 了解 / 5 できない) |
| 受け取るもの | `text`(**`ch`、`from`、`from_name`** が付く)、`ack`(本部に届いた)、**`config`(チャンネルの一覧)**、**`mode`(一斉の切り替え)** |
| 音声 | **HTTP の `POST /api/voice`**(§9) |
| 番号(seq) | 起動のたびに乱数から始めて 1 ずつ足す |
| 時刻(ts) | Wi-Fi があれば NTP、無ければ GPS、どちらも無ければ 0 |

**自宅サーバーへの道(2026-11-17 に決定: 端末は外からつなぐ。Cloudflare のトンネルを使う)**

```
 端末 --Wi-Fi--> インターネット --wss(443)--> Cloudflare --トンネル--> 自宅サーバー
                                                                      ├ ブローカー(WebSocket の入口)
                                                                      └ サーバーと管理画面
```

- Cloudflare のトンネルの公開先が運べるのは、Web の通信(HTTPS と WebSocket)。**MQTT をそのまま(1883 番や 8883 番で)は通せない。** だから、MQTT を WebSocket に載せる。
- 暗号化と証明書は Cloudflare が受け持つ。端末は、公開の認証局の証明書の束で相手を確かめる(自分で証明書を作って配らなくてよい)。
- ルーターの転送も、ファイアウォールの変更も要らない。自宅の IP アドレスも出ない。
- 公開の入口になるので、**ブローカーは、名前とパスワードの無い接続を受け付けない。** 端末ごとに名前(= 端末 ID)とパスワードを持ち、自分の分のトピックだけを使える。
- 接続先のホスト名、名前、パスワードは `secrets.h`(git に入れない)に置く。**このリポジトリは公開なので、ホスト名も書かない。**
- 自宅サーバーの側は、2026-11-17 に準備した(ブローカーの認証、端末ごとの制限、WebSocket の入口。サーバーの上で確認済み)。トンネルの行き先も足してあり、外から PC でつないで確かめた(認証つきで通る)。**実機(T-Beam)からの接続が、まだ。**
- 管理サイトは、ログインが無い検証版なので、手前に名前とパスワードを聞く入口を置いて、外に出してある。音声の送り先(HTTP)も、同じ入口を通ることになる(端末にも、その名前とパスワードを持たせる)。
- 暗号化を使うとメモリを数十 KB 使う。BLE・録音と同時に足りるかは要確認(BLE だけのときの空きは約 219KB)。

### 8.2 LoRa(ほかの端末。緊急時)

- フレームの形・署名・重複の判定・中継の待ち時間・送信時間の予算は、前に作って PC でテストしたものを使う。
- 経路: **Wi-Fi で MQTT につながっていれば MQTT。だめなときだけ LoRa。**
- 受信したフレームは、①自分あて・全員あてなら画面へ、②中継を予約、③自分が MQTT につながっていれば、**受け取ったバイト列のまま** `reray/v1/up/gw/{自分}/lora` へ流す(サーバーの `GATEWAY_RAW_FORMAT` の方式)。
- LoRa で運ぶのは、定型信号と指示コードだけ。**チャンネルの文と音声は運ばない。**
- 報告フレームの中身は、サーバーの項目(`pos`、`n`、`dir`)に合わせて直す。フレームの形の正本を共通仕様に置くことと合わせて、サーバー担当と決める(サーバー側の分解は未実装)。

### 8.3 電波法のガード(前と同じ。変えない)

- **LoRa の送信は `RERAY_TX_ENABLE=1` のビルドだけ。既定は 0。** `COMPLIANCE.md` の確認欄は 2026-11-17 に書き入れた。使うチャンネルは 923.2MHz。残りは、周波数の固定と送信前の電波確認の実装(`COMPLIANCE.md` §4.2)。これが済むまで、1 のビルドを作らない・書き込まない。まず屋内で試す。
- 出力は 12dBm を超える設定だとビルドが失敗する。周波数は確認欄で決めたチャンネルだけ。送信前のキャリアセンスと、送信時間の予算(仮の値: 1 回 200 ミリ秒以下、1 時間 18 秒以下)を通ったときだけ送る。
- 送信が無効のビルドでは、LoRa は受信だけ動く。緊急時に Wi-Fi が切れていて送れないときは、「今は送れません(つながったら送ります)」と出して取っておく。
- したがって v2 は、**まず Wi-Fi と BLE で、平常時と緊急時の全部の画面が動く形**で完成させる。LoRa の送信は、確認欄が埋まった日に有効にする。

今のサーバーには、文字になったものを受け取る口(`source = transcript`)は既にある。
